# CARLA 场景编辑器开发维护手册

这套软件把场景编排、CARLA 物理运行和实际轨迹重放连成一条可检查的数据链。维护时首先要保住三件事：车辆控制只有一个最终执行者，记录时间能够对应真实采样帧，失败后能恢复世界并留下可解释的结果。界面上的“运行成功”不能代替实验指标验收。

本手册面向后续开发者和接手仓库的智能体，代码与协议基线为 **2026 年 10 月 10 日**，最近一次实验可行性复核为 **2026 年 10 月 17 日**；新增验证与未决问题见第十一节。默认工作目录是仓库根目录；当前部署在 `E:\Scene_package\Scene_HYX`，其他机器可以使用不同路径。自定义地图在 CARLA 中的名字为 `package/Maps/map10/map10`。地图网格、材质和 UE 工程不随此仓库分发。

先熟悉实际操作时，阅读[用户手册](user-manual.md)；定位实现时按第一节的文件顺序；修改代码前检查第四、六节的运行约束；完成后按第八、十一节验证和交接。

2026 年 10 月 10 日的审核记录包含 111 项 Python 回归、22 项前端回归、26 个交通交互场景及 14 次录制、重放和预设运行。证据在 `optimization_reports/code_audit_20261010/summary.json` 及其引用的日志中。这些结果属于当时的代码、地图和参数；修改后必须重新选择并执行相应验证，不能沿用旧的通过数字，也不能据此声称零 BUG。

## 一 先建立正确的系统边界

浏览器负责编辑与展示。Flask 服务负责校验、保存和启动工作进程。每次实际运行创建独立 Python 工作进程，由它连接 CARLA、生成参与者、推进仿真、记录结果并清理。关闭浏览器不等于工作进程停止。

“导出可运行 .py”走另一条启动路径：服务仅在下载时校验草稿并生成脚本；之后用户运行该脚本，脚本直接调用 `scene_studio.engine.Session` 并连接 CARLA，不需要 Flask。脚本仍依赖项目的运行模块，不是脱离项目的独立二进制。两条路径复用同一仿真与记录引擎，不应同时控制一个 CARLA 世界。

```text
浏览器草稿
  → 校验及路线预演
  → 固定本次场景快照
  → 服务端创建运行目录并启动工作进程
  → CARLA 物理运行或录制姿态重放
  → 轨迹与遥测逐帧落盘
  → 清理资源和恢复世界
  → 保存最终结果
  → 发布 finished 或 error
```

“预演”使用简化模型显示路线和速度估计；“实机布置预览”会在 CARLA 创建参与者，但关闭其物理并允许拖动时间，运动模式使用估计位置，环境模式使用已录制姿态；“运动编排运行”实际计算车辆物理；“固定轨迹环境重放”逐帧设置录制姿态。这四种状态不能共用一套实验有效性判断。

### 主要文件及阅读顺序

1. [server.py](../scene_studio/server.py)：HTTP 接口、场景保存、进程生命周期和命令投递。它直接启动 `scene_studio.engine`，不是旧的 `runner` 主程序。
2. [schema.py](../scene_studio/schema.py)：完整场景的规范化与验证。添加参数首先考虑此处的范围、类型和兼容性。
3. [timeline.py](../scene_studio/timeline.py)：时间轴求值、行为预设、运动哈希、手动控制权。主要逻辑不依赖 CARLA，适合离线验证。
4. [planning.py](../scene_studio/planning.py) 与 [routing.py](../scene_studio/routing.py)：道路连通规划、预演路径、CARLA 地图接口适配。
5. [engine.py](../scene_studio/engine.py)：当前运行入口、单步循环、截图帧资格、手动接管及环境重放。
6. [runner.py](../scene_studio/runner.py)：仍被当前引擎继承的基础会话、事件动作和车辆控制器。文件名带有旧实现含义，但当前功能仍依赖它，不能作为废代码删除。
7. [optimized_control.py](../optimized_control.py)、[traffic_math.py](../traffic_math.py)、[agents/navigation/controller.py](../agents/navigation/controller.py)：跟车、运动约束、PID 油门制动与转向计算。
8. [recording.py](../scene_studio/recording.py)：实际轨迹写入、录制完整性和重放读取；[scene_runtime.py](../scene_runtime.py) 负责停止信号、资源登记和分阶段清理。
9. [web/app.js](../scene_studio/web/app.js)、[web/sequencer.js](../scene_studio/web/sequencer.js)：编辑草稿、异步请求、时间轴拖动、运行状态与输入设备。Three.js 依赖已放在 `web/vendor/`。
10. [export_python.py](../scene_studio/export_python.py)、[exported_scene.py.txt](../scene_studio/exported_scene.py.txt)：生成含场景快照的单个 `.py`、在本地直接运行 CARLA、显示相机、投递手动输入并保存驾驶输入日志。`/api/export-python` 只负责导出，不持有运行进程。

`tools/` 同时包含验收工具、场景生成器和修改地图资产的旧工具。维护编辑器时不要批量运行整个目录，尤其不要顺手执行车道线、材质或 XODR 修改工具。

## 二 安装 启动与版本确认

已验证的环境为 Python 3.10 和 CARLA 0.9.15。依赖由 [requirements-studio.txt](../requirements-studio.txt) 管理，包括 CARLA Python API、Flask、NumPy、OpenCV、Pygame、NetworkX 和实机验收使用的 Requests。Node.js 用于前端离线测试，不是浏览器界面的运行服务。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-studio.txt
.\.venv\Scripts\python.exe -m scene_studio.server
```

先启动 CARLA，打开 map10 并进入 Play，再访问 `http://127.0.0.1:8877/`。`Start-SceneStudio.cmd` 优先使用仓库 `.venv`，其次尝试本机 Python 3.10，最后使用 PATH 中的 `python`。不要把开发机的用户名或解释器绝对路径复制成其他机器的安装要求。

编辑器默认端口为 **8877**。本轮审核在 **8879** 启动单独的服务以确认新代码；这只是当次部署选择，默认值没有改成 8879。报告使用过的 **8766** 是静态报告服务，也不负责控车。需要指定编辑器端口时运行：

```powershell
.\.venv\Scripts\python.exe -m scene_studio.server --port 8879
```

CARLA 连接地址目前在服务端和基础运行器中固定为 `127.0.0.1:2000`，并没有统一的远程主机配置界面。修改地址需要同步检查服务端、工作进程和测试工具。一个编辑器端口可以有独立的进程状态，但不同编辑器服务仍会争用同一个 CARLA 世界；不能同时运行。

服务只绑定本机，写请求要求 JSON，并检查本机 Host 与浏览器 Origin。它不是面向公网的多用户服务。不要仅修改监听地址便当作完成远程部署。

Python 服务未启用热重载。改完后先正常结束当前运行，再退出旧服务并启动新服务；仅刷新浏览器不会加载新的服务端代码。首次启动会把缺失的模板复制到 `studio_data/scenes/`，不会覆盖已有同名场景。

## 三 场景 计划与运行数据如何流转

### Python 导出与独立运行

`POST /api/export-python` 接收当前场景草稿、`hz`（10/20/40/60）和浏览器保存的 `input_config`。服务端复制草稿、设置 `dt=1/hz`、运行场景校验与固定轨迹基准校验，然后把规范化场景和输入标定嵌入模板。响应是可下载的 `.py`；下载不启动 CARLA，也不修改草稿。新增字段时同时核对导出序列化、运行入口及前端下载逻辑，避免编辑器运行与脚本运行含义分叉。

生成脚本先定位项目根目录（`--project-root`、`HYX_SCENE_ROOT`、脚本父目录、导出时路径），再调用 `Session(scene, run_folder).run()`。每次创建 `studio_data/runs/py_<时间>_<随机值>/`，保存 `scene.json`、`launcher_manifest.json` 和 `console.txt`；引擎继续生成 `run_manifest.json`、`status.json`、`take.json`、`telemetry.csv`、`trajectory.jsonl`、`events.json` 及相机画面。窗口运行还写 `driver_input.csv`，含原始/归一化输入、仿真时刻和单调时钟；`--no-window` 不采集窗口输入。眼动由外部系统采集，不得把没有眼动列误写成采集故障。

本地 Pygame 窗口读取 `frame.jpg`，使用与引擎已有的 `commands/` 和 `input.json` 协议发送接管、释放与驾驶指令。窗口中的摄像头刷新率与 CARLA 物理步长不同，输入约每 50 ms 采样一次；正式实验需用硬件与显示器另测。关闭窗口或按 Q 可提前停止，判断数据是否覆盖设计时长看 `take.json.covers_scene_duration`，不能只看 `status.json=finished`。脚本异常应写 `status.json=error` 和 `console.txt`，引擎的 `finally` 负责世界设置、天气和自有对象恢复。环境模式的 `locked_take` 是同一运行库中的基准目录名，移动项目时需连同基准录制一起保留。

### 场景 JSON 是用户意图

场景输入接受版本 1 或 2，`validate()` 返回深拷贝并归一为 `version: 2`。`mode` 为 `motion` 或 `environment`；后者通过 `locked_take` 指向同一运行库中的基准目录。它不是任意文件路径。

顶层核心字段包括 `id`、`name`、`map`、`duration`、`dt`、`ego`、`actors`、`events`、`look` 和 `camera`。`actors` 定义模型、位置、初始速度、行为、路线及片段；`events` 定义条件触发动作。主车必须是开始时生成的车辆。

位置单位为米，角度为度，速度配置和遥测速度为 km/h，加减速度配置为 m/s²。CARLA 内部速度向量使用 m/s，转换应在明确的边界完成。`dt` 允许 1/60、0.025、0.05 或 0.1 秒，场景时长必须是它的整数倍。不要靠截断最后一帧时间掩盖不匹配。

片段类型为速度、制动、变道、跟车和灯光。速度片段支持线性或平滑变化，结束后保留目标值；变道累积横向偏移。制动和跟车按片段窗口生效，灯光结束后恢复进入片段前的状态。当前并没有通用的任意参数关键帧系统。

同一车辆的速度与制动属于同一纵向通道，横向偏移与变道属于同一横向通道；跟车和灯光各自独立。同类启用片段不能重叠，同一通道不能同时存在启用事件和启用片段，以免事件刚执行就被时间轴覆盖。独立通道可以组合。若以后需要叠加，必须先明确覆盖、恢复和优先级规则，不能只删校验。

条件包括时间、坐标、两参与者距离、接近某点、速度和前置事件。前置依赖不能成环。`enabled`、初始生成等字段必须是真正的布尔值，字符串 `"false"` 不等于 `false`。schema 只核验模型类别及配置结构；模型是否存在、位置是否被占用和路线是否连通，还要分别经过蓝图库、规划与生成检查。

事件在推进下一步之前，按 `events` 数组顺序读取当前快照，每个事件只触发一次。同一帧可以触发多个事件；零延迟前置事件若排在前面，后件可以同帧触发，反过来通常要等下一步。新增触发器需要明确这类顺序影响。距离条件使用两参与者中心的 XY 距离，不是保险杠净距；进入某范围要使用 `<=`，其默认比较方向是 `>=`。

当前循环写入 `duration` 的终帧后直接停止，不再检查该时刻条件；恰好设在设计终点的时间事件不会执行。使用者应将结束标记至少提前一个 dt，并通过实际末帧核验终点。未来若调整终点事件语义，需要同时定义触发、记录及 finish 动作的顺序，并增加边界回归。

事件与片段的名字相同，也不代表持续时间相同。事件制动会持续到后续速度动作清除，制动值 0 是无油门滑行；片段制动则在窗口结束后解除。事件变道使用行驶距离，片段变道使用秒数。`route` 动作重新规划演员已有路线，不从动作体读取新的路线数组。维护时先看动作执行代码，再确定界面说明。

### plan JSON 是可重建的规划产物

当前 `planner_version` 为 **2**。计划含 `motion_hash`、`duration`、`tracks` 和 `warnings`；每条 track 包含 `path`、`lane_width` 与预演 `frames`。路径行是 `[累计距离,x,y,z,yaw]`，预演帧是 `[时间,x,y,z,yaw,速度]`。

计划只提供路线和简化估计，不计算车辆动力学、碰撞、实际跟车或完整条件事件。规划器会考虑速度片段及速度事件可能需要的最大路程，但事件真正何时触发仍由运行器决定。条件路径、路线终点和延迟生成都要在实际轨迹中检查。

引擎同时检查规划器版本与运动哈希，旧计划或其他场景的计划会重算。改动规划结果含义时应提高 `PLAN_VERSION`。服务端还保留少量内存计划及地图缓存；当前地图缓存按名字识别，同名地图重新导入后应重启服务，不能假设缓存自动识别全部地图资产变化。

### take 和 manifest 回答不同问题

新 `take.json` 为 **version 2**，保存基准场景、天气、dt、实际记录时长、帧数、运动哈希、`trajectory_sha256`、降采样路径和完成标志。`trajectory.jsonl` 每行保存一个正式仿真时刻的参与者状态与控制归属。

`complete=true` 表示记录段正常关闭且有足够帧，**不表示跑完计划全程**。判断是否覆盖全程要看 `covers_scene_duration`，判断是否适合研究还要看关键事件、碰撞、速度、接管及剔除规则。正常提前停止可以产生可重放的短记录段。

读取时会检查帧数、递增时间、dt、参与者、主车存在性、有限数值和运动标识；版本 2 还校验轨迹字节的 SHA256。版本 1 有历史哈希兼容分支，但没有新轨迹摘要，不能据此追溯证明所有旧数值未被修改。重放按实际记录时间寻找最近帧，不把记录行号一律当成理想时间。

运动哈希排除 `look`、`camera`、参与者名称与颜色等字段，但参与者片段整体进入哈希，灯光片段仍属于锁定配置，不能概括成所有外观改动都被排除。哈希还保留会影响运动的前置事件链。例如制动依赖天气事件之后发生，修改天气事件的触发时刻会改变运动哈希，修改天气外观本身则不会。新增动作时必须重新判断这条边界。

`run_manifest.json` 保存 Python 与 CARLA 版本、地图名、OpenDRIVE 摘要、指定运行代码摘要、规范化场景摘要、dt、seed 和开始时间。**当前没有显式 manifest 版本字段**；以后扩展格式应先设计兼容规则。它的代码摘要覆盖引擎列出的控制与规划文件，不等于整个仓库指纹；XODR 摘要也不等于地图网格、材质、天空和碰撞资产都相同。正式实验还需保存仓库版本及 UE 资产版本。

`started_unix_ns` 在预热前写入，是现实墙钟时间，不能直接当成实验零时刻。`take.weather` 保存用于环境合成的基准底层天气，也不是整段运行中所有天气变化的历史；运行中的变化应结合事件记录读取。

现有 `look` 事件日志只保存预设名称和时刻，没有保存实时自定义 weather/camera 覆盖值；相机视角切换也未完整留档。启动快照和 manifest 无法补回这些即时变化。正式试次应固定起始条件；调试中临时修改须另存参数，未来增加动态视觉条件时应补全记录协议。

### 一个运行目录应如何读取

服务端创建 `studio_data/runs/<run_id>/`，先写场景快照与计划，再启动工作进程。后续文件作用如下：

- `console.txt`：工作进程输出与异常栈。
- `status.json`：当前或最终状态，适合轮询；事件与碰撞只保留最近一部分供显示。
- `telemetry.csv`：按时间及参与者展开的实际帧、姿态、速度来源和控制输入。
- `trajectory.jsonl`、`take.json`：完整重放数据及其校验信息。
- `events.json`：完整事件、碰撞、截图采样索引及世界恢复结果。
- `frame.jpg`：最新显示画面；`shot_*.jpg`：每个仿真秒首张符合资格的截图。
- `commands/`、`input.json`：本次会话的命令队列和最新驾驶输入。

不要单独复制 `take.json` 后删除轨迹文件。分享环境场景至少同时保留完整基准运行数据及对应场景；研究归档最好保留整个运行目录。

同名字段还要看所属文件。`status.frame_count` 是相机回调计数，`take.frame_count` 是轨迹行数；前者不能用于检查轨迹缺帧。`take.manual_override` 表示录制帧中出现过手动 owner，`events.manual_override` 来自会话的环境轨迹偏离标记；普通物理运行手动驾驶可能前者为 true、后者为 false。汇总数据时应命名区分，不能简单合并成一个研究标签。

图文教程实操时补修了录制列表排序：`ordered_run_folders()` 按 manifest 的 `started_unix_ns` 倒序排列，无有效 manifest 的旧记录回退到场景快照文件时间。不要再按文件夹名排序，否则 `case172_` 前缀会把更新的编辑器录制挤出列表。列表跳过损坏记录后再执行 40/60 项上限；该问题新增 2 项回归，增补后的完整离线结果为 113 项 Python、22 项前端检查通过，原审核报告保留其历史计数。

遥测的 `id` 是场景内逻辑标识，`carla_id` 是本次引擎实例标识。跨运行比较使用前者并确认场景对应关系；生成、销毁会使轨迹中参与者键出现或消失。`speed_source=recorded` 表示使用源录制速度，不能将它解释为重放车辆当前物理测速。

## 四 仿真循环必须维持的约束

### 每个世界只有一个推进时钟的客户端

同步模式表示 CARLA 等待客户端发出 tick 才推进下一步。固定步长决定一步仿真经过多少秒，不保证一步只消耗同样长的现实时间。引擎记录预计下一帧号，再调用 `world.tick()`；返回帧号不符便报错停止，避免其他客户端同时推进世界。

服务端启动前要求世界为异步状态且开启渲染。工作进程保存原设置，启用同步与固定步长，并设置物理子步。只有引擎主循环推进 tick。规划、HTTP 请求、传感器回调和外部诊断线程都不得偷偷推进世界。

暂停时正式 `elapsed` 不前进，但仍可能推进 CARLA 帧来刷新画面和处理命令。参与者物理被冻结，恢复时按模式恢复物理与保存的速度。因此 CARLA 帧号差不能在包含暂停的整段记录中直接乘 dt 作为试次时间。

### 每辆车只有一个最终控制输出

`StudioDriver` 继承基础 Driver，但覆盖启动控制线程的入口，避免旧接口再创建第二个持续控制者。主循环先处理命令和控制权，再计算时间轴、跟车、目标速度斜坡及 PID，最后向车辆应用控制。事件线程即使需要等待变道完成，也不能另建持续写入油门和转向的循环。

`VehicleControl` 是油门、制动、转向等输入，`apply_control()` 提交输入，本身不保证车辆达到目标速度。场景的加减速度限制主要约束控制目标的变化，不等于实际车辆加速度上限。制动仍要保留路线转向；不要为处理制动而提前返回零转向。

### 正式记录帧资格独立于回调到达时间

生成参与者后先预热，再释放制动、按配置初始化速度和重置控制器。预热 tick 不属于实验时间轴。运动运行使用初始化结束时的 `initial_snapshot` 作为第一行遥测；环境重放先应用源轨迹零时刻并完成相应 tick，再确定第一行。

`first_recorded_frame` 是首帧下界，`recordable_frames` 则明确列出可归档截图的帧：初始记录帧，以及每个真正前进的 moving tick。仅判断“帧号大于首帧”不够，暂停后的帧也满足这个条件，却不属于正式轨迹。

预计下一帧的时间映射和正式帧资格必须在调用 `world.tick()` **之前**登记，因为相机回调可能早于主循环写入 CSV。映射和资格集合共同保留最近 250 帧，不能只清理其中一个。相机重建时还通过 generation 与图像锁阻止旧回调写入新会话。

`frame_times_map` 关联 CARLA 帧号和采样时刻。相机回调可能迟到，必须使用图像自己的 `image.frame` 查表，不能使用回调发生时的 `elapsed`。延迟到达的暂停帧即使此时已经继续运行，也不能进入正式截图；合格运行帧即使到达时已经暂停，仍可按其原时刻处理。

截图保存该秒首张合格图像，文件名使用真实采样毫秒，并在 `events.json.camera_samples` 保存文件、时间及帧号。不要求每秒整点恰好有图像，也不保证零时刻一定存到图片。找不到映射的相机帧计数并跳过；碰撞无法映射时保留 `null`，不要伪造时间。映射缓存有界，异常长的回调延迟也需调查。

相机实际采样间隔为 `max(dt, 1/fps)`。例如 dt 为 0.05 秒时，即使相机配置写 60 FPS，也不能承诺每个仿真秒采样 60 张；界面 `camera_fps` 则统计最近回调的现实到达率。这些指标都不是被试显示器真正呈现的帧率。

### 三个输入标识不能混用

`run_id` 指明哪一次运行，防止旧页面操作新会话；`epoch` 是控制权代数，每次接管或释放递增；`seq` 是同一次控制权下递增的输入序号。工作进程同时校验控制权和新旧输入，拒绝旧代数与重复、倒序序号。

新客户端所有命令都应携带 `run_id`。当前 `/api/command` 为兼容旧调用仍允许省略它，但浏览器已统一附加；`/api/input` 必须提供。接管命令返回 queued 仅表示排队，客户端应轮询状态确认 owner 与新 epoch 后再发驾驶输入。

输入中断超过约 0.35 秒时，控制权仍留在手动模式，输出转向 0、油门 0、制动 1。看门狗使用单调现实时间，避免仿真暂停后超时失效。不要通过自动释放控制权来“修复”断连，否则车辆可能自行继续行驶。

## 五 HTTP 接口与可执行示例

接口集中在 `server.py`。写入均使用 `Content-Type: application/json`；错误通常返回 JSON 的 `error` 字段，校验及部分内部异常使用 400。不要把所有 400 都当作用户配置错误，内部异常仍需查日志。图像与视频端点不返回 JSON。

### 读取接口

- `GET /api/connection`：连接状态、地图、版本、同步与渲染设置，以及预设和动作目录。
- `GET /api/map`、`GET /api/blueprints`：道路与环境包围盒、可用参与者模型。
- `GET /api/scenes`、`GET /api/scenes/<sid>`：场景列表与规范化完整场景。
- `GET /api/status`、`GET /api/current-scene`：当前运行状态和启动快照。
- `GET /api/takes`、`GET /api/takes/<rid>`：录制库列表与基准元数据。
- `GET /api/runs`、`GET /api/runs/<rid>/<filename>`：近期运行和白名单文件下载，包括 manifest、计划、轨迹、遥测、事件、状态与截图。
- `GET /api/frame`：最新 JPEG，暂无图像返回 204；`GET /api/video`：持续 JPEG 流。

`/` 提供编辑器，`/static/` 提供本地前端；`/research/<path>` 只服务视觉研究报告目录。下载接口不接受任意路径，不要为了新增一个文件就删除白名单或路径检查。

### 场景编辑与启动

`POST /api/validate`、`POST /api/scenes` 和 `POST /api/plan` 的请求体直接是完整场景。`POST /api/preset` 使用 `{scene,actor,preset,target?}`。`POST /api/snap` 使用 `{x,y,z?}`。`POST /api/start` 使用 `{scene,preview:false}`，不会自动切图。

下面先读取本地已有模板并验证，只有执行最后两行才会实际启动。运行前确认 CARLA 空闲，模板位置适合当前地图；如默认端口不同，只修改 `$api`。

```powershell
$api = 'http://127.0.0.1:8877/api'
$scene = Get-Content -Raw -Encoding UTF8 'scene_studio/templates/Following_Demo.json' | ConvertFrom-Json
$body = $scene | ConvertTo-Json -Depth 40
$valid = Invoke-RestMethod "$api/validate" -Method Post -ContentType 'application/json' -Body ([Text.Encoding]::UTF8.GetBytes($body))
$startBody = @{scene=$valid.scene; preview=$false} | ConvertTo-Json -Depth 40
$started = Invoke-RestMethod "$api/start" -Method Post -ContentType 'application/json' -Body ([Text.Encoding]::UTF8.GetBytes($startBody))
```

保存会把旧版本备份到 `studio_data/history/`，再原子替换场景文件。启动保存的是请求快照，不会自动把编辑草稿写入场景库。

### 控制命令与结果确认

`POST /api/command` 支持 `stop`、`pause`、`resume`、`camera`、`look`、`action`、`transform`、`manual`、`takeover`、`release`、`seek`。其中 `manual` 是旧客户端兼容入口，新输入使用 `/api/input`。`seek` 仅用于实机预览；移动参与者也限于运动模式的布置预览。环境锁定模式拒绝修改运动和位置。

```json
{"type":"takeover","owner":"keyboard","run_id":"实际运行ID"}
```

确认 `/api/status.control.owner` 与 `epoch` 后向 `/api/input` 发送：

```json
{"run_id":"实际运行ID","epoch":1,"seq":1,"steer":0,"throttle":0.3,"brake":0}
```

这里的 epoch 和运行 ID 必须取自当前状态，不能照抄示例常量。转向范围 −1 至 1，油门和制动范围 0 至 1；制动优先，不能同时要求正油门。停止使用 `{"type":"stop","run_id":"实际运行ID"}`，随后等待终态并检查结果。queued 不证明命令执行成功；运行状态中的 `command_error` 也必须处理。

## 六 结束 发布与异常恢复

正常停止与异常都进入 `finally`。当前顺序是关闭遥测、关闭相机并等待已有图像写入、清理登记资源、恢复天气、恢复原世界设置、检查残留参与者、关闭录制与重放、保存事件结果，最后写终态。单项清理失败必须记录错误并继续后续独立恢复步骤。

`finished` 是结果可读取的发布信号。不能先写 finished 再读取远程天气或写 `events.json`，否则紧接着开始分析或重放的客户端会读到缺失文件。保存结果失败时要发布 error 并保留先前错误。磁盘完全不可写时连错误状态都可能无法落盘，此时以进程退出及控制台日志定位，不能制造成功文件。

工作进程发布终态后，Python 解释器可能仍在退出。服务端仅对已经 finished/error 的同一进程有界等待，最多 5 秒；超时提示“仍在收尾”。活跃预览、运行和暂停都不能被新启动误杀。不要用无限等待或强制杀进程解决连续运行竞态。

清理只针对本次登记的参与者和资源。发现同步世界残留时，先确认是否仍有其他客户端拥有它，再决定恢复；禁止通过销毁全部车辆或盲目切为异步来掩盖未知进程。修改退出路径时必须用故障注入证明：一个传感器销毁失败、遥测关闭失败或天气 RPC 失败，不会跳过世界设置恢复。

## 七 增加功能应沿着整条链检查

例如新增“速度上下限随时间变化”，不能只在界面多放两个输入框。先规定上下限交叉、缺省值、插值方式、与跟车及制动的关系，再依次处理：

1. **schema**：字段类型、范围、引用、旧版本默认值与冲突规则。
2. **前端**：属性输入、时间轴表现、复制撤销、保存、切换场景和错误反馈。
3. **timeline**：纯函数插值、边界时刻及结束后是否保留。
4. **planner**：预演如何估计；不具备的物理能力明确写入 warnings，必要时提高规划版本。
5. **runtime**：谁读取参数，如何转成控制，暂停、事件、接管和恢复自动时是否一致。
6. **recording**：是否影响运动哈希、是否新增必须记录的数据、旧录制如何兼容。
7. **测试与文档**：正常路径、非法配置、异步竞态和实际交通互动均有适用证据。

前端新增异步操作必须保留请求快照和版本判断。保存过程中用户继续编辑时，旧响应不能覆盖新草稿；路线请求返回时，要确认仍对应当前场景且没有正在拖动；拖动取消要恢复旧值。运行期间草稿编辑锁与服务器校验要同时存在，不能只依赖按钮禁用。

引入新记录字段时写明单位、采样时刻、空值含义和来源。研究指标应从完整记录计算，不从状态接口最近几十条数据推算全程。不要把目标速度命名为实际速度，也不要把回放速度当作当前物理传感量。

## 八 回归验证如何选择

修改运行逻辑或界面交互时，先运行与问题对应的最小回归，再执行完整离线检查，避免只证明新增函数能运行：

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
node tests/frontend_audit.mjs
git diff --check
```

配置、接口和哈希变化重点看 `test_audit_server.py`、`test_scene_studio.py`、`test_studio_timeline.py`；控制、帧资格、清理看 `test_audit_engine.py` 与 `test_audit_finalization.py`；轨迹格式与计划兼容看 `test_audit_recording.py`。前端测试运行实际函数并模拟网络与界面依赖，仍需真实浏览器补关键交互。

以下修改需要 CARLA 实机验证：车辆控制及初始化、路线规划、dt、相机帧映射、暂停恢复、手动输入、生成销毁、录制与重放。实机前让地图空闲，确认没有其他推进时钟的任务。一次只运行一组：

```powershell
.\.venv\Scripts\python.exe tools/test_audit_live.py --port 8877
.\.venv\Scripts\python.exe tools/run_case172.py --ids P02 P13
```

第一条串行执行录制重放、暂停接管、重复环境重放及七种预设，并检查全部相关截图对齐。第二条用于指定场景复测；修改公共控制或路由后应执行 `--all`，再运行 `tools/audit_case172_delivery.py`。这组场景不是任意车型参数的速度精度认证。

实机完成至少检查：状态没有 error，研究要求的事件按顺序发生，实际运动达到本次设定的验收条件，截图帧可对应遥测，重放按设定容差一致，世界设置与天气恢复，本次参与者已清理。针对速度标定还需独立统计稳态误差、超调、稳定时间、制动距离和横向偏差。

`tools/build_code_audit_report.py` 汇总已有证据，不会替代测试。新代码摘要与旧运行不一致时，应让旧结果显示为过期；不能改摘要或放宽检查来恢复绿色状态。保留首轮失败日志和修复后的复测结果，便于追踪发现过程。

部分验收工具把输出目录写成特定日期，例如本轮 `code_audit_20261010`。运行前读清楚输出路径，先保留已有证据，并为新的审核使用独立目录或调整明确的报告配置，不要无意覆盖上一轮结果。纯文档修改只需核对事实、生成一致性、链接和阅读布局，无须因此启动 CARLA。

## 九 按症状定位问题

**页面打不开或仍是旧行为。** 确认实际端口、服务进程命令行和工作目录。检查是否仅刷新了浏览器而没有重启 Python；前端模块还可能使用缓存。不要为了“刷新”同时启动多个控制服务。

**场景列表整体失败。** 查看场景目录是否有损坏 JSON。先复制损坏文件到备份位置，再隔离并验证；不要删除全库。单个文件的格式错误可能影响列表读取。

**连接成功但启动失败。** 查 `/api/connection` 的地图名、同步模式与渲染设置，再查 `console.txt`。常见原因是已有客户端控制 tick、模型不存在、生成位置重叠或路线不连通。区分 schema 拒绝、工作进程启动失败与 CARLA 生成失败。

**预演看着正确，实车却停下或走偏。** 比较运行目录的场景快照、计划终点及遥测。跟车、条件事件和碰撞未被预演完整模拟；路线耗尽也会停车。检查计划版本和运动哈希，不能把预演线当作实际轨迹。

**接管无效或突然刹停。** 看 owner、epoch、last_seq、failsafe，确认输入属于当前 run_id，浏览器有焦点且输入在持续发送。先理解看门狗为何触发，不要关闭它。实物方向盘还需单独核验轴向、死区、踏板与浏览器支持。

**图像与事件时间不一致。** 以 `camera_samples` 的帧号连接遥测，排查预热帧、暂停帧、旧相机 generation 和未映射帧。最新 `frame.jpg` 用于显示，不能代替带时间索引的研究截图。

**结束后缺文件或下一场启动被拒。** 查最终 error、文件时间和工作进程是否真实退出。收尾提示表示正在等待旧进程，不代表可以并行启动另一套脚本。若进程意外退出而状态未终结，服务端会报告工作进程退出；保留现场后再恢复。

**速度波动。** 先核对当前目标、事件、跟车和制动输出，再比较车型、初始化方式与位置。已有 Audi 20 km/h 目标短段出现过 14.42–22.84 km/h；原因尚不能简化成某一个增益。初速注入、车辆动力学及控制器响应要用对照实测分离，不能为通过场景测试就宣称速度精度达标。

## 十 备份 恢复与研究边界

代码进入版本控制，运行和被试数据另行备份。`.gitignore` 排除了 `studio_data/`、`optimization_reports/`、媒体、日志与本地环境；一次 git 提交并不会保存这些实验成果。至少备份场景库、保存历史、使用过的完整运行目录、验收报告、代码版本和地图资产版本。

正式备份前先正常停止并等待结果发布，复制到新的带日期目录，保留原件并检查数量与摘要。不要移动活动运行目录，不要用大范围递归删除腾空间。整理数据时按研究记录确认哪些基准仍被 `locked_take` 引用。

目前应明确保留以下研究限制：

- seed 只被记录，尚未统一驱动参数随机抽样；未来增加抽样必须保存实际抽到的值和顺序。
- 固定步长不是实时性能保证，界面 FPS 也不是完整仿真吞吐量；传感器采样、图像到达、屏幕呈现、按键发生和控制应用之间的现实延迟尚未完整测量。
- 每秒截图不足以定位毫秒级风险显现或人的反应时。正式人因实验应建立完整时间链和试次有效性规则。
- 环境模式关闭车辆物理并重放姿态，适合视觉条件对照，不能用于检验雨天摩擦如何改变车辆运动。
- 重放中接管后，主车恢复物理，背景车仍沿录制轨迹；这不代表双方都会响应的闭环交通。释放后不会把主车传送回基准，也不会清除 `manual_override`。
- 环境重放不会重新执行场景事件，包括其中的天气与 marker 动作；静态 look 和运行中的 look 命令可以生效。需要按时变化的视觉条件应另行定义并验证，不能假设旧事件会自动重演。
- 车型、车速、路面和转弯条件仍需独立标定；速度区间、连续安全参数关键帧与二维安全场尚未形成完整功能。

## 十二 手册如何维护

两份可编辑正文为 `docs/user-manual.md` 和 `docs/developer-maintenance-manual.md`。浏览器中的 `scene_studio/web/guide.html` 与 `scene_studio/web/maintenance.html` 由正文生成，不应直接编辑生成页。编辑器原有的“使用说明”入口仍指向 `guide.html`。

只在需要生成文档时安装文档依赖，再从仓库根目录执行：

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-docs.txt
.\.venv\Scripts\python.exe tools/build_manuals.py
.\.venv\Scripts\python.exe tools/build_manuals.py --check
```

`--check` 验证网页是否与正文一致，不覆盖文件。生成器同时检查章节锚点与本地文件引用。文档依赖不加入编辑器运行依赖，阅读网页也不需要外网或构建工具。

修改界面按钮、控制含义、默认值、文件格式或启动方法时，同步更新对应手册，并在本机编辑服务的 `/static/guide.html`、`/static/maintenance.html` 检查实际阅读布局。网页中的代码文件名只作仓库索引，Markdown 源文件保留可打开的相对源码链接。版本日期表示核对基线；新的测试数和硬件支持必须有证据才更新。

用户手册现包含 13 张真实操作截图，原始 PNG 保存在 `scene_studio/web/manual-assets/`，采集过程记录在同目录 `capture-log.json`。`docs/manual-figures.json` 保存黄色框的原图像素坐标和编号说明；生成器把它们作为 HTML 叠加层显示，不改写原始截图。正文使用相对路径的普通 Markdown 图片，网页支持点击放大、原始尺寸和 Esc 关闭。

界面布局变化后，应从真实操作重新截图，再调整标注坐标；不要通过替换图片上的按钮、文字或运行状态制造不存在的界面。截图统一为 1280×720，若改变尺寸，还需同步元数据及放大视图样式。验证所有图片可加载、标注指向正确、关闭放大后焦点返回、窄屏仍可阅读；演示运行结束后检查自有对象清理和世界恢复。
